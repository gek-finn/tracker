# Одноразовый технический релиз SQLite backup

Это отдельная ветка от **9229b82d838a5a93301cc6c5b4361807abea2a14**.
Исходные app.py, db.py, backup.py, seed_demo.py, схема, интерфейс и Procfile
не изменены. Локальный публичный деморежим в этот релиз не входит.
Действующий deployment: ced1c23c-142f-47e3-8272-438b252cda28.

## Границы гарантий

Новый WSGI entrypoint получает проверенную независимую копию **до import app**.
При ошибке конфигурации, копирования, проверки или сохранения состояния импорт
не выполняется и worker не запускается. Это может вызвать недоступность сервиса.
Релиз с volume требует короткого перерыва; нулевой риск/простой не обещается.

После создания копии импортируется неизменённое старое приложение. Оно может
выполнять init_db и process_recurrences при импорте и просмотре страниц.
Копия сохраняет состояние ДО этих операций, но исходная база после импорта
не становится read-only. Подавление старых операций в этот релиз не входит.
Старый helper Basic Auth также не исправляется: Unicode-пароль безопасно
обрабатывается именно временным download middleware, независимо от helper.

Backup API читает источник через mode=ro без immutable и включает committed
данные WAL. Исходный journal_mode не меняется, checkpoint и очистка журналов
источника не выполняются. SQLite может записывать служебный WAL-index/SHM.
Если чтение требует восстановления hot journal, операция отказывает.
Только файл КОПИИ приводится к DELETE и закрывается перед проверкой/выдачей.

## Состояние на volume

При TASK_TRACKER_DB=/data/demo.sqlite3 используется:

```
/data/.technical-backups/<BACKUP_JOB_ID>/
  job.lock
  snapshot.sqlite3
  ready.json
  import-allowed.json
```

Каталоги создаются с mode 0700, файлы с 0600 на POSIX. Это не static-каталог.
Готовые файлы не заменяются: публикация hard-link от проверенного временного
файла атомарно отказывает при существующем имени. Файловая система должна
поддерживать hard links и обычные SQLite-блокировки.

ready.json фиксирует source path, исходную revision, job ID, deadline,
SHA-256 и размер. Пароля, ключа и текстов задач в нём нет.
import-allowed.json записывается и синхронизируется ДО попытки import app.

Повторный старт проверяет ту же копию и использует её без нового capture.
Если исходная база позже изменилась, snapshot остаётся прежним.
Повреждение/пропажа готового файла или противоречивое состояние означает
отказ запуска. Нельзя удалять/редактировать служебные файлы ради «починки».
Сбой между публикацией файла и манифестом также требует ручного разбора:
готовый файл не перезаписывается. Собственный pending-файл обычной неудачной
попытки удаляется; неизвестные файлы после аварии не удаляются автоматически.
ОС снимает lock при завершении процесса; файл job.lock удалять не нужно.

Не менять BACKUP_JOB_ID при restart/redeploy: новый ID означает новое задание,
а не восстановление прежнего. Полное внешнее удаление каталога задания нельзя
отличить от первого запуска. Сохранность volume и metadata обязательна.

## Настройки будущей публикации (СЕЙЧАС НЕ ПРИМЕНЕНЫ)

Цель: virtuous-stillness / production / web, существующий web-volume → /data.
Сначала отдельно согласовать короткое окно обслуживания и деплой.

| Переменная | Назначение |
|---|---|
| TRACKER_ENV | production, сохранить |
| TASK_TRACKER_DB | /data/demo.sqlite3, сохранить |
| TRACKER_ADMIN_PASSWORD | существующий admin-пароль, не раскрывать |
| TASK_TRACKER_SECRET | существующий постоянный секрет, не менять |
| BACKUP_JOB_ID | один фиксированный безопасный ID, например pre-public-demo-01 |
| BACKUP_EXPIRES_AT | абсолютное время UTC в Unix seconds, например на 30 минут после согласованного начала |
| BACKUP_DOWNLOAD_KEY | новый случайный secrets.token_urlsafe(32), только в защищённом окружении |
| BACKUP_DOWNLOAD_ENABLED | строго 1 для временного скачивания; 0 закрывает маршрут |
| BACKUP_TIMEOUT_SECONDS | 30 по умолчанию, допустимо 1..30 |

Не помещать секреты в Git, URL, argv, скриншоты, командную историю или логи.
Генерировать ключ через password manager/защищённый способ и вносить через
Railway Variables вручную. Не использовать известные тестовые значения.

Custom Start Command будущего технического релиза:

```sh
gunicorn --workers 1 --threads 4 --timeout 90 --bind 0.0.0.0:$PORT backup_entrypoint:application
```

Pre-deploy остаётся пустым. Seed/миграции в команду не добавлять.
BACKUP_EXPIRES_AT должен совпадать с ready.json на рестартах: продление
через изменение переменной намеренно отклоняется. Истечение срока закрывает
скачивание, но не мешает перезапуску с уже проверенной копией.

При максимуме 30 секунд ensure_snapshot и 30 секунд проверки import marker
подготовка имеет запас до timeout 90; зависание файловой системы/старого app
всё равно может привести к завершению worker со стороны Gunicorn.
Не добавлять --reload. --workers 1, --threads 4 выбирает gthread в Gunicorn.

Сервис должен быть доступен публике только через HTTPS edge Railway.
Middleware доверяет одному X-Forwarded-Proto от этого прокси (ProxyFix), как
базовое приложение. Прямой отдельный публичный container port недопустим.

## Порядок разрешённой позднее публикации

1. Сверить project/service/environment, текущий deployment ID и SHA.
   Сохранить старую команду, имена/наличие переменных и путь volume без
   раскрытия значений секретов. Подтвердить доступность прежнего образа.
2. Запустить тесты технической ветки на временных базах, включая POSIX-тест
   Gunicorn. Проверить diff: исходные файлы базового коммита не изменены.
3. После отдельного разрешения подготовить commit/push этой ветки. До push
   проверить правила автодеплоя: никаких случайных обновлений main.
   Локальные доработки деморежима не включать.
4. В рамках ОДНОГО согласованного deploy применить новый код, backup-настройки
   и новую Custom Start Command. Не применять настройки отдельным рестартом
   старого app:app. Не использовать Pre-deploy: там нет подключённого volume.
5. Новый worker создаёт/проверяет snapshot, записывает marker, импортирует app.
   Дождаться healthcheck /healthz. При ошибке не удалять metadata, не менять
   ID и не пытаться автоматически пересоздать источник или готовую копию.
6. Сразу скачать и независимо проверить копию. На время операции не выполнять
   административные изменения. Просмотр старых страниц тоже может генерировать
   повторения; он не меняет уже готовый snapshot.

## HTTPS-скачивание

Маршрут `/__maintenance/backup` поддерживает только GET/HEAD. Он требует
HTTP Basic admin и X-Backup-Key, проверяемые до открытия файла. Никаких
публичных ссылок, параметров пути, token в URL, CORS-доступа или создания
новых копий на GET нет. OPTIONS/POST не создают/не возвращают копию.

В локальном интерактивном терминале с установленными зависимостями проекта:

```powershell
python download_backup.py https://<домен-сервиса> E:\private-backups\tracker-before-update.sqlite3
```

Каталог назначения должен существовать; файл назначения НЕ должен существовать.
Клиент скрыто запрашивает пароль и временный ключ. Он не следует redirect,
проверяет TLS-сертификат, размер, SHA-256, integrity_check и таблицы tasks и
recurrences. Готовый файл публикуется локально без перезаписи существующего.
Лимит клиента для этой маленькой demo DB: 64 MiB. При обрыве можно повторить
скачивание до deadline. Незавершённый файл не становится готовой копией.

Сервер отдаёт private, no-store; attachment; SHA-256 и размер. Исходный source
path и содержимое таблиц не выдаются в диагностике. SHA по тому же HTTPS
каналу обнаруживает повреждение передачи, но не является независимой
криптографической аттестацией сервера при компрометации сервера/TLS.

Сохранить две проверенные локальные копии в разных защищённых местах.
Только потом считать резервирование завершённым. Не импортировать app для
локальной проверки файла: это могло бы запустить миграции/повторения.

## Завершение и удаление механизма

После проверки копий отдельно согласовать отключение BACKUP_DOWNLOAD_ENABLED
и ключа. Это может вызвать restart/deploy и повторный импорт старого app.
Deadline сам закрывает download даже без ручного отключения.

Следующим согласованным релизом удалить временные модули и настройки,
вернуть выбранную постоянную WSGI-команду. Не удалять серверный snapshot до
подтверждения независимых копий; очистку volume согласовать отдельно.
После удаления проверить отсутствие download endpoint. Не считать смену
команды обратно на app:app безопасной для исходной DB: старый app опять пишет.

## Восстановление / откат

Откат образа НЕ восстанавливает SQLite и может снова запустить старые
миграции/повторения. При ошибке backup startup импорт запрещён намеренно;
доступность может пострадать. Не обходить этот барьер неподтверждённым rollback.
При сбое import app после marker готовая копия остаётся на volume, но worker
не обслуживает HTTP. Исправление этого состояния требует отдельного решения.

Этот релиз НЕ содержит upload/restore/delete HTTP-маршрутов. Если SSH,
Console и Volume Files остаются недоступны, удалённое восстановление нельзя
выполнить данным download-only механизмом. Потребуется восстановление доступа
либо отдельно согласованный maintenance-релиз для восстановления. Не добавлять
обходной restore endpoint без отдельного разрешения.

Когда есть согласованный maintenance-доступ:

1. Остановить ВСЕ процессы, использующие исходную DB; не импортировать app.
2. Проверить SHA-256 и integrity_check сохранённого файла. Сохранить отдельную
   страховочную копию текущего состояния и связанных файлов до любых замен.
3. Доставить проверенную копию в закрытый staging-каталог volume.
4. Только при гарантированно остановленном приложении выполнить существующий
   CLI восстановления с ЯВНЫМ --db, после отдельного подтверждения:

   ```sh
   python backup.py restore /data/incoming/verified.sqlite3 --db /data/demo.sqlite3
   ```

   Утилита заменяет базу и удаляет старые sidecars. Её проверка свободной
   блокировки не доказывает отсутствие idle-процессов: остановку обеспечить
   организационно. Без интерактивной консоли --yes допустим только внутри
   отдельно согласованной maintenance-процедуры, не в обычной Start Command.
5. Проверить восстановленный файл без app, выбрать код без неожиданных
   стартовых изменений и лишь затем запустить приложение.

Не восстанавливать поверх работающего Gunicorn и не удалять live WAL/SHM.

## Локальные тесты

```sh
python -c "import tests.base; import unittest; r=unittest.TextTestRunner(verbosity=1).run(unittest.defaultTestLoader.discover('tests',top_level_dir='.')); raise SystemExit(not r.wasSuccessful())"
```

Первый import tests.base направляет исходный bootstrap app во временную DB.
Новые тесты также используют только TemporaryDirectory. Отдельно:

```sh
python -m unittest tests.test_technical_snapshot tests.test_technical_http tests.test_technical_client tests.test_technical_entrypoint -v
```

На Windows Gunicorn POSIX-тест пропускается; вместо него выполняется настоящий
локальный WSGI HTTP smoke-test с Werkzeug. Это НЕ заменяет запуск Gunicorn
на Linux. Команда POSIX-теста перед публикацией:

```sh
python -m unittest tests.test_technical_entrypoint.EntrypointTests.test_gunicorn_one_worker_four_threads -v
```
